## 2. Proposals (what the artifact shows for each item)

Facts checked before writing these:
- Samples on the Pi already come back after a restart or shutdown. Mixxx loads `samplers.xml` at start, and `mixxx-save-on-change` rewrites it within a second of every pad change (R-13 PASS on build B; pads 1-2 have survived every restart and reboot today).
- Loaded effects already come back after a clean quit or shutdown: stock Mixxx writes `effects.xml` at exit and reads it at start (`src/effects/effectsmanager.cpp:56,76` at `3ebac449`). A power cut loses effect changes made since the last start. The Starlight script also resets every effect's depth (`meta` 0.6) and both units' mix at start (Starlight study, JS 94-102).

## 3. The review artifact

A private claude.ai page, **"MixPi UI review"**, that the owner works through on the web. It holds every item above, the current shots, the proposed mockups, the component guide, and a tracker.

### Page structure
1. Header: the name, one line (round 1, 17 Nov 2026, test card on build B), and a status summary with a filter.
2. **Screens**: one card per item s1-s14 (s8/s9 and s13/s14 may share a card). Each card has:
   - Now (the shot) beside Proposed (the mockup), stacked on a phone.
   - The owner's words as a quote.
   - The proposal as bullets.
   - Any questions.
   - The status control.
   - The notes thread with an add-note box.
3. **Everywhere**: cards g2-g6.
4. **Components & tuning**: the guide (section 4).
5. **Ideas for later**.

### Tracker (the `db` capability)
- Item text, shots and mockups are page content. Statuses and notes live in `db` so the owner's choices persist and Claude can read them back.
- `status/{itemId}`: `{state, from: "owner"|"claude", at}`. `state` is one of:
  - `proposed` (the default when there is no doc)
  - `agreed`
  - `change` (the owner wants something different)
  - `building`
  - `on-card`
  - `done`

  The owner can set any state.
- `notes/{autoId}`: `{item, text, from: "owner"|"claude", by: <user id>, at}`. Notes written by the page are `from: "owner"` (labelled with the viewer's name via `user.profiles`). Claude writes `from: "claude"` through ArtifactData, and the page labels those "Claude".
- Capabilities: `{db: {}, user: {}}`. Signed-out or no db: the page still renders everything read-only with a short notice.

### Primitive class API (builder C writes the real CSS; builder B uses only these names plus its own `mxl-` layout classes)
- `.mx-screen`: an 800×480 frame with `--mx-bg`.
- `.mx-btn`: 44 px tall, `--mx-radius`, uppercase `--mx-font-ui` 15 px.
  - Modifiers: `--confirm`, `--sound`, `--deck1`, `--deck2`, `--play`, `--cue`, `--caution`, `--danger`, `--ghost`.
  - States: `.is-on`, `.is-disabled`.
- `.mx-close`: a 44×44 square with a red ✕.
- `.mx-tabs`, `.mx-tab.is-on`: the top bar.
- `.mx-seg` with `.mx-seg-opt.is-on`: a segmented choice.
- `.mx-slider` with `.mx-slider-fill` and `.mx-slider-thumb` (set `--v: 0..1` on `.mx-slider`); the fill takes the full height of the track.
- `.mx-menu` with `.mx-menu-item` (plus `.is-on`, `.has-sub`, `--danger`): a list or menu row, 52 px.
- `.mx-chip` with `--usb`, `--sync`, `--master`, `--inuse`, `--ready`, `--caution`: 2 px radius.
- `.mx-popover`: a sheet over a dimmed screen, with a header, a body and a footer of buttons.
- `.mx-toggle.is-on`: an ON/OFF switch.
- `.mx-deckrow`: the deck info row (title, artist, chips, time, BPM, pitch, key) with the truncation rule from s6.

### Component roles (the guide's backbone; builder C may tune)

| Role | Meaning | Examples | Look |
|---|---|---|---|
| Navigate | Moves you around; changes nothing | tabs, Back, menu rows, ☰, Sources items | neutral surface, light text; current = accent underline or edge |
| Choose | Picks one setting or mode | segmented options, FX 1/FX 2, routes | neutral; chosen = accent surface and accent text |
| Confirm | Does the thing you came for | LOAD, LOAD TO PAD, DONE, OPEN | muted accent fill, dark text |
| Sound | Changes what is heard now | ▶, CUE, pad TRIGGER, SYNC, KEY, Q, LOOP, effect ON | transport or deck colour; outline at rest, filled when lit |
| Caution | Takes something away; can be redone | EJECT, pad STOP, HIDE, CANCEL scan | orange outline at rest, orange fill when pressed |
| Danger | Cannot be undone | CLEAR (n), delete, the close ✕ glyph | red; always behind a confirm step except ✕ |

### Builders (Claude Opus 5.5, medium; native agents; no shared files)
- **A, page and tracker:** `shell/index.html`. Page layout, theme (light and dark), responsive, all item content from section 2 in a page-local data list, Now shots from `shots/`, mockup slots filled from `<template id="mx-…">` elements, the components slot, the tracker on `db` and `user`, and a read-only fallback.
- **B, screen mockups:** `mockups/fragments.html` (one `<template id="mx-<mockup id>">` per mockup in section 2) and `mockups/layout.css` (only `.mxl-` classes). Uses only the primitive API. A local stub of the primitives is for previews only.
- **C, components and tuning:** `components/tokens.css`, `components/primitives.css` (the API above), `components/section.html` (the guide: the roles table with live specimens, every primitive in its states, Now vs Proposed for buttons, slider, menu item, chips and close, radius and colour notes).
- **Orchestrator (packaging):**
  - Inline the CSS and templates into one page.
  - Render every mockup once to check it.
  - Send fixes back to the builder who owns that part.
  - Publish with `shots/` as files.
  - Seed the statuses: s1, s4, s10 and s12 are `agreed`; the rest are `proposed`.
  - Do one db read-back.
  - Give the owner the link.
